## AI 활용 방식

설계 검토, 명세 작성, 실측 로그 분석, 문서와 테스트 작성은 Claude(AI)와 대화하며 진행했습니다. 구현은 그 명세를 바탕으로 제 PC에서 진행했고, 구현 보고와 교차 검토 의견을 다시 가져와 명세와 대조했습니다. 무엇을 만들지, 어떤 선택지를 쓸지, 실기에서 어떻게 확인할지는 제가 정했습니다.

AI의 제안을 받아들이지 않거나 고친 사례:

1. **목표를 다시 설명해 방향을 바로잡음.** AI는 처음에 게임을 코어 하나에 모으는 방향을 권하지 않았습니다. 이 프로젝트의 대상이 스레드 하나가 일을 거의 다 하는 게임이라는 점을 다시 설명해 설계 방향을 바꿨습니다.
2. **"남는 CPU 최소 2개" 제안을 거절함.** 논리 CPU가 적은 PC를 위해 규칙을 더하자는 제안에, 그런 PC는 비우지 않아도 부족한 건 마찬가지라는 이유로 넣지 않았습니다. AI도 SMT 없는 CPU에서는 문제 자체가 생기지 않는다는 점을 놓쳤다고 인정했습니다([0004](0004-reserve-whole-dominant-core.md)).
3. **배포 제안을 사용자 기준으로 바꿈.** 런타임을 따로 설치하게 하는 방안은 거절했습니다. exe 하나로 묶는 제안은 "최상단에는 exe 하나, 나머지는 하위 폴더"로 바꿨습니다. 특정 게임의 권한을 확인해서 필요할 때만 관리자 권한을 요청하자는 제안은 "특정 게임에 맞추지 말고 항상 요청"으로 바꿨습니다([0005](0005-simple-package-and-admin.md)).
4. **더 줄일 수 있는지 계속 물음.** 확정한 계획에 대해 "결과에서 거꾸로 따져 더 간단한 방법"을 찾게 해서 측정 방식을 통째로 바꿨고([0001](0001-measure-without-moving-game.md)), 이후 명세에서도 "요구사항을 위한 최소한의 구현이 맞는지" 다시 물어 필요 없는 구조 4곳을 걷어냈습니다.
5. **교차 검토로 명세의 빈틈을 고침.** 구현 전 교차 검토에서 나온 지적(변경마다 복구 기록 남기기, 측정 순서, L3 후보를 먼저 거르기 등)을 받아 명세를 고쳤습니다.
