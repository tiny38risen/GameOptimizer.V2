# 0001. 측정 중에는 게임을 건드리지 않는다

- 날짜: 2026-11-16
- 결정: 지영

## 문제

지배 스레드를 올릴 코어를 고르려면 코어마다 속도와 방해 요소(인터럽트·DPC)를 알아야 합니다. 처음 v3 설계는 측정하는 동안 게임 전체를 물리 코어 하나에 모으고, 모든 코어를 정방향·역방향으로 옮겨 다니며 재는 방식이었습니다.

## 선택지

| | A. 게임을 코어마다 옮기며 측정 | B. 게임은 그대로 두고 측정 (선택) |
|---|---|---|
| 코어 속도 | 실제 게임 부하에서 잰 실효 클럭 | 우리 프로세스의 프로브 스레드로 잰 정수 연산 처리량 |
| 인터럽트·DPC | PDH 카운터 | PDH 카운터 (같음) |
| 측정 중 게임 설정 변경 | 있음. 변경마다 복구 저널 기록, 측정 후 원복과 확인 필요 | 없음. 측정 단계에 복구할 것이 없음 |
| 측정 시간 | 8코어 기준 약 16초 | 10초 이내 ([0002](0002-ten-second-overlapped-measurement.md)) |
| 게임 영향 | 측정 내내 코어 하나에 묶임 | 프로브가 코어를 잠깐씩 씀 |
| 약점 | 구현과 검증할 실패 경로가 많음 | 합성 부하의 순위가 게임 부하와 다를 수 있음 |

## 결정

B. 결과를 바꾸는 입력은 코어 속도, 인터럽트·DPC, 토폴로지 세 가지이고, 셋 다 게임을 건드리지 않고 얻을 수 있다고 봤습니다.

## 이유

A안의 패치 계획을 확정한 뒤, 같은 기능을 더 간단하게 만들 방법이 있는지 결과에서 거꾸로 따져 보게 했습니다. 적용 후 성능을 좌우하는 상태(지배 스레드가 가장 빠른 코어에서 혼자 도는 것)에서 거꾸로 보니, 측정 중 게임을 옮겨야만 얻을 수 있는 값은 어차피 적용 단계에서 치워지는 부하뿐이었습니다.

당시 판단: "더 가볍고 짧은 과정에서 같은 결과(아마도)를 받는다."

"아마도"인 이유는 세 가지 전제(접근 가능한 프로세스는 적용 때 치워진다, 코어 간 속도 차이는 주로 부스트 클럭에서 나온다, 특정 코어에 고정되는 부하는 주로 인터럽트·DPC다)가 맞아야 하기 때문입니다. 그래서 B로 구현하고, 진단 로그에서 전제가 깨질 때만 A를 붙이기로 했습니다.

## 결과

- 측정 단계의 복구 코드가 통째로 빠졌습니다. 측정 중 중단하거나 게임이 꺼져도 되돌릴 것이 없습니다.
- "아마도"의 전제는 진단 로그로 확인했습니다. 2026-11-18 실측 17회에서 지배 스레드는 지배 논리 CPU의 97.0~99.9%를 썼고, 지배 논리 CPU에 남은 다른 부하는 0~1.5%였습니다([원자료](../../measurements)).
